# Agent-mode context-window management (research)

Research ticket: [Cal3574/scriptorium#151](https://github.com/Cal3574/scriptorium/issues/151).
Map: [#144](https://github.com/Cal3574/scriptorium/issues/144) ("AI reading companion - agent widget map").
Depends on the resolved data model in [#146](https://github.com/Cal3574/scriptorium/issues/146) (`agent_threads` + `agent_messages`) and the resolved tone in [#149](https://github.com/Cal3574/scriptorium/issues/149) ("Socratic partner").
Scope: how Agent mode should keep a per-user-per-book thread bounded as it accumulates dozens to hundreds of turns over weeks, without breaking the companion's conversational continuity.
Out of scope (per the ticket): auth, SSE transport mechanics, quota metering.

## Recommendation

**Trigger: message count, not token count.** Summarize when a thread's `agent_messages` row count crosses a fixed threshold (proposed: 40 messages, i.e. ~20 turns). Turn count is a proxy Scriptorium can compute with a `COUNT` the repository already knows how to write (see `QueriesRepository.countThisMonth` for the existing pattern) and needs no new dependency. The repo has no token-counting utility today, and Anthropic's own `messages.count_tokens` endpoint is a network round trip that would add latency and a second billed-adjacent call to every turn just to decide whether to trim - disproportionate for a per-book chat where turns are short (1500-token response ceiling, typically much less) and the far end of "weeks of reading" is still nowhere near Sonnet 5's 1M-token window. A message-count trigger is simple, deterministic, and cheap to evaluate on every turn.

**Mechanism: hybrid - last N turns verbatim + one rolling summary of everything older, plus the thread's seed message always pinned.** Concretely:
- Keep the most recent 20 messages (~10 turns) verbatim.
- Fold everything older than that into a single `runningSummary` string on `agent_threads`, re-summarized (old summary + newly-aged-out messages -> new summary) every time the threshold is crossed again.
- Always additionally pin the thread's very first message (the highlight-to-discuss seed, with its `highlightedPassage`) into the assembled history even after it ages out of the verbatim window, since it is the anchor the entire thread's Socratic opening reacted to.
- A pure sliding window (drop oldest, no summary) was rejected: it silently erases the reader's specific earlier reactions and questions, which is exactly the continuity the "Socratic partner" tone in #149 depends on ("prefer a good question back", "react to why the reader picked that passage" - both require remembering what was already asked and answered). A pure LLM-summarize-everything approach was rejected because it pays a summarization call on every single turn once the thread is long, and it flattens the most recent, highest-signal exchange into paraphrase right when it matters most for the next reply. The hybrid keeps the cheap common case (below threshold: no summarization call at all, unchanged behavior) and only pays the extra LLM call periodically (once per ~20 messages), while the verbatim tail keeps recent back-and-forth exact.

**Where it runs: inline, synchronously, but after the turn's answer has already streamed to the client - not before it.** Concretely, in the Agent equivalent of `QueryService.run`, after `yield { type: 'done', answer }` (mirroring `packages/api/src/queries/query.service.ts`), check the message count and, if the threshold is crossed, run one more synchronous LLM call to refresh `runningSummary` before the generator (and therefore the request) completes. This was chosen over the alternatives for a concrete reason: the repo has exactly one background-job system today (`packages/worker` + BullMQ, wired for the PDF ingest pipeline in `packages/providers/src/queue`), and it is purpose-built for long, multi-stage, resumable book processing - not for a fire-and-forget per-chat-turn side effect. Standing up a second job type, a queue, and a worker consumer for something that runs once every ~20 messages is infrastructure the product does not need for v1. A background job would also reintroduce exactly the kind of race the existing turn/failure semantics in #146 were designed to avoid (a summary write racing a new user turn's history read). Doing it synchronously-but-after-`done` means: the visible answer is not delayed (the client already received its `done` event and can render), the extra latency only exists on the connection's tail and only on the rare turn that crosses the threshold, and there is no new infrastructure. A lazily-computed-and-cached approach (summarize opportunistically on read) was rejected because "read" here is the SSE stream itself - there is no separate read path to lazily hook into, and it would make the first read after a long thread reopen pay the summarization latency in the middle of the user's request instead of predictably at the end of the turn that crossed the threshold.

**Schema/code changes:**

`packages/database/src/schema/agent-threads.ts` (new, alongside the `agent_messages` table from #146) gains two nullable columns:
```ts
runningSummary: text('running_summary'),
// Boundary: messages with createdAt <= this are represented by
// runningSummary, not replayed verbatim. Timestamp (not a message FK) to
// match the existing createdAt-ordering convention used by
// queries_user_id_created_at_idx - no join needed to find the boundary.
summarizedThroughCreatedAt: timestamp('summarized_through_created_at', {
  withTimezone: true,
}),
```
Both null until the thread first crosses the threshold - a fresh or short thread behaves exactly as #146 originally specified, with zero schema-visible change.

History assembly - the Agent-mode analogue of `QueriesRepository`/`QueryService` (would live as an `AgentThreadsRepository` in `packages/server-core` and an `AgentService` in `packages/api`, mirroring `queries.repository.ts` / `query.service.ts`) - changes its history-read step from "all messages, skip unanswered" (#146's resolution) to:
1. Read the thread row for `runningSummary` / `summarizedThroughCreatedAt`.
2. Read messages with `createdAt > summarizedThroughCreatedAt` (or all messages, if null), in order, skipping any user message with no assistant reply (unchanged from #146).
3. If `runningSummary` is set, prepend it as a synthetic first `LlmMessage` (e.g. `{ role: 'user', content: '[Earlier in this conversation: <summary>]' }` folded into the system prompt instead is also viable - either placement works since `ClaudeLlmClient.stream()` takes a plain `LlmMessage[]`; putting it in the system prompt alongside the existing Socratic-partner `SYSTEM_PROMPT` constant keeps the roles list unions clean).
4. Always ensure the thread's first message (by `createdAt`) is present verbatim even if older than `summarizedThroughCreatedAt` - re-fetch it by id if the range in step 2 already excludes it.
5. Map to `LlmMessage[]` and call `ClaudeLlmClient.stream()` exactly as today.

The summarization call itself is a second, separate `LlmClient.complete()` (non-streaming - nothing needs to reach the client) call with its own small system prompt instructing the model to preserve the reader's specific reactions/questions/opinions as concrete statements, not to paraphrase the book's content, and to merge with the previous `runningSummary` if one exists. This constant would live next to `SYSTEM_PROMPT` in the Agent mode's synthesis-prompt module (the equivalent of `packages/api/src/queries/synthesis-prompt.ts`).

**Failure-mode analysis:**

What the companion visibly "forgets" under this design: the *exact wording* of anything more than ~10 turns back collapses into whatever the summarization pass chose to keep. If the reader made a sharp, specific remark 15 turns ago that the summary compressed into a blander paraphrase, the companion's later callback to it will be slightly generic rather than a precise echo. Repeated re-summarization (summary-of-a-summary, each time the threshold is re-crossed) also risks gradual drift/"telephone game" loss over very long threads (hundreds of turns).

Acceptability for v1: mostly acceptable given the product's own framing. The Socratic-partner voice (#149) is explicitly short-turn and present-focused - it leans on the last few exchanges and the seed highlight far more than on verbatim recall of turn 3 of a 50-turn conversation, and it is allowed to ask a clarifying question back rather than assume perfect memory. The one piece worth being deliberate about, and which this design already builds in as a cheap mitigation: **always pinning the thread's seed message** (the original highlighted passage + the reason the companion opened on) so the "why this passage" anchor never degrades into summary paraphrase, since that is the one piece of context #149's resolution explicitly said the opening line must react to specifically, not generically.

Cheap mitigation if drift turns out to matter in practice: instruct the summarization prompt to retain the reader's own phrasing as short quoted fragments for their 2-3 most distinctive remarks, rather than prose paraphrase - this costs nothing extra to build (it is a prompt change, not a schema change) and can be tuned after real usage shows whether generic paraphrase is actually a problem.

**Not recommended for v1, but worth flagging as a complementary, near-zero-cost lever:** enable top-level prompt caching (`cache_control: { type: 'ephemeral' }`) on the assembled history in `ClaudeLlmClient.toParams()`. Because history assembly is append-only up to the verbatim window, the growing prefix is cache-friendly and a cache hit is 10x cheaper than a fresh read. It was not folded into the core recommendation because it does not address the actual problem this ticket is about (the eventual context-window ceiling still needs trimming regardless of caching) and because Scriptorium's own usage pattern - a reader picking a book back up after hours or days away - will miss the 5-minute (or even 1-hour) cache TTL on most turns, so the savings would be inconsistent in practice. Worth a follow-up ticket, not a blocker for this one.

## Supporting research

### 1. `claude-sonnet-5` context window and pricing

Per the official model page ([platform.claude.com/docs/en/models/sonnet-5/overview](https://platform.claude.com/docs/en/models/sonnet-5/overview)):
- **Context window: 1,000,000 tokens** (1M is both the default and the maximum for this model; no smaller-context variant exists).
- **Max output: 128K tokens** per response (Scriptorium currently caps this far lower, at `max_tokens: 1500`, per `DEFAULT_MAX_TOKENS` in `packages/providers/src/llm-client/claude-llm-client.ts`).
- **Pricing: $2 / MTok input, $10 / MTok output** - confirmed on both the model page and the dedicated pricing page ([platform.claude.com/docs/en/about-claude/pricing](https://platform.claude.com/docs/en/about-claude/pricing)). This is Sonnet 5's now-standard (no longer "introductory") price; a scheduled September 2026 increase to $3/$15 was cancelled.
- **Prompt caching rates** (same pricing page): a 5-minute cache write costs 1.25x base input ($2.50/MTok), a 1-hour write costs 2x base input ($4/MTok), and a cache read/hit costs 0.1x base input ($0.20/MTok).
- **No long-context surcharge:** the pricing page states explicitly that Claude 4.6-and-later models including Sonnet 5 "include the full 1M token context window at standard pricing... A 900k-token request is billed at the same per-token rate as a 9k-token request." So the cost problem this ticket is about is pure linear growth from replaying more history every turn, not a tiered-pricing cliff.

**Illustrative math** (not exact billing - a sanity check on scale, not a forecast): assume an average turn is roughly 150 input tokens (reader's message) + 120 output tokens (the companion's 2-3 sentence reply), so replaying history at turn *n* costs roughly `270 * n` input tokens on top of the fixed system prompt. At turn 100 that is ~27,000 tokens of pure history replay, ~$0.054 at $2/MTok, on *every subsequent turn* until the thread ends. Because that replay cost grows linearly with every turn, the *cumulative* cost of replaying history across an entire growing thread (an arithmetic series) grows roughly quadratically with turn count - for an illustrative 300-turn thread that is on the order of `270 * 2 * 2 * 300 * 300 / 2 / 1e6 ≈ $24` in replayed-history charges alone across the thread's life, separate from the cost of each turn's own new content. That is the actual cost problem this ticket exists to solve: not proximity to the 1M-token ceiling (a ~300-turn thread at ~270 tokens/turn is roughly 80K tokens, well under 10% of the window), but the fact that naive full-replay cost keeps climbing forever with no bound, long before the context window itself would ever be the limiting factor for a single-book companion thread.

Sources: [Claude Sonnet 5 model page](https://platform.claude.com/docs/en/models/sonnet-5/overview), [Claude Platform pricing](https://platform.claude.com/docs/en/about-claude/pricing).

### 2. How comparable products handle unbounded conversation history

**a. Anthropic's own guidance and shipped features** ([Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), Anthropic engineering blog) names three patterns for long-running agent context, with tradeoffs:
- **Compaction (summarize-and-restart):** "the practice of taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary." Anthropic's own caveat: "overly aggressive compaction can result in the loss of subtle but critical context whose importance only becomes apparent later" - the same failure mode flagged above for Scriptorium's rolling summary.
- **Structured note-taking / agentic memory:** the agent periodically writes durable notes outside the context window (e.g. a scratchpad file), giving "persistent memory with minimal overhead," at the cost of depending on the agent's own discipline about what it chooses to record.
- **Sub-agent architectures:** delegate focused sub-tasks to separate agents with their own clean context, coordinated by a main agent - good separation of concerns, but adds architectural/coordination overhead that is out of proportion to a single-book chat companion.

Anthropic also now ships **compaction as a first-class API feature** ([Compaction docs](https://platform.claude.com/docs/en/build-with-claude/compaction)), available on `claude-sonnet-5` among other current models: enable it via the beta header `compact-2026-01-12` and `context_management.edits: [{ type: 'compact_20260112' }]` on `client.beta.messages.create`. It triggers automatically once input tokens cross a configurable threshold (default 150,000, minimum 50,000), has the model generate a summary server-side, returns it as a `compaction` content block, and the API then silently drops everything before that block on subsequent requests as long as the caller keeps appending the *full* `response.content` (not just extracted text) back into the message list. This was evaluated and **not recommended for Scriptorium's v1** for three concrete reasons: (1) its minimum trigger threshold (50K input tokens) is far above where Scriptorium's cost problem actually bites (the illustrative math above shows meaningful cumulative cost well under 50K tokens of replay); (2) it requires persisting and replaying opaque `compaction` content blocks verbatim, which does not fit `agent_messages`' current flat `content: text` column shape from #146 without a structural change; (3) it is a beta feature with its own versioned strategy type (`compact_20260112`) that Anthropic could revise, versus a bespoke `runningSummary` string Scriptorium fully controls and can tune the exact prompt for (matters for preserving the reader's specific phrasing, per the Socratic-partner constraint). It is worth revisiting if the hand-rolled approach proves inadequate at scale, or if `agent_messages` later gains richer structured content.

**b. LangChain's memory abstractions** (widely used, well-documented reference implementations of the same tradeoff, not Scriptorium's stack but a credible worked comparison): `ConversationBufferWindowMemory` implements a pure sliding window - "only uses the last K interactions"; when a new interaction pushes the count past K, "the oldest interaction is discarded" outright, with no record kept. `ConversationSummaryBufferMemory` is explicitly the hybrid pattern this research recommends: it "summarizes the earliest interactions in a conversation while maintaining the `max_token_limit` most recent tokens in their conversation... allows for the retention of distant interactions [while] the buffer ensures that recent interactions are not lost." ([Pinecone: Conversational Memory for LLMs with Langchain](https://www.pinecone.io/learn/series/langchain/langchain-conversational-memory/); [LangChain `ConversationSummaryBufferMemory` reference](https://reference.langchain.com/python/langchain-classic/memory/summary_buffer/ConversationSummaryBufferMemory)). The one difference from Scriptorium's recommendation above: LangChain's summary-buffer variant triggers on a token budget, which assumes a token-counting utility is already in place - Scriptorium has none today, hence recommending a message-count trigger instead as the v1-appropriate approximation of the same idea.

**c. Retrieval-augmented history** (mentioned for completeness, not selected): rather than compressing older turns, index them (e.g. by embedding) and retrieve only the ones semantically relevant to the current turn. This is architecturally what Ask library already does for book content (`QueriesRepository.retrieveCandidates`, pgvector cosine search over `chunks`), so the *infrastructure* exists in this repo - but Agent mode was explicitly decided to have **no retrieval tool in v1** ("constrained to given context... no book-search tool in v1," map #144's decisions). Applying retrieval to the conversation's own history (not book content) would be a new capability, adds embedding-per-message cost and complexity, and cuts against the Socratic partner's framing as a present, continuous conversation rather than a lookup tool - it is the RAG pattern the map decisions already steered Agent mode away from. Not recommended.

## Summary of the decision matrix

| Question | Decision | Why |
|---|---|---|
| Trigger | Message count (40 messages / ~20 turns) | No token-counting utility exists; count is cheap and already the repo's pattern (`countThisMonth`) |
| Mechanism | Hybrid: last 20 messages verbatim + rolling summary of the rest + pinned seed message | Pure window loses the reader's specific continuity the Socratic tone needs; pure per-turn summarization is wasteful and blurs the most recent exchange |
| Where it runs | Inline, synchronous, after the turn's `done` event | No existing job infra fits a per-turn side effect this small; avoids a race with the next turn's history read; doesn't delay the visible answer |
| Schema change | `agent_threads.runningSummary` (text, nullable), `agent_threads.summarizedThroughCreatedAt` (timestamptz, nullable) | Matches the nullable-until-needed pattern already used by `queries.answer` / `queries.citations`; timestamp boundary needs no join, consistent with the existing `createdAt`-ordered index convention |
| Biggest accepted loss | Exact phrasing beyond the last ~10 turns | Acceptable for a short-turn, present-focused Socratic voice; mitigated by always pinning the seed highlight message |
